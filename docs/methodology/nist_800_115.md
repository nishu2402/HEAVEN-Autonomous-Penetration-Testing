# HEAVEN ↔ NIST SP 800-115

Mapping of HEAVEN modules against [NIST SP 800-115 (Technical Guide to
Information Security Testing and Assessment)](https://csrc.nist.gov/publications/detail/sp/800-115/final).

NIST 800-115 is methodology-centric rather than test-list-centric, so this
mapping is per section. HEAVEN automates the full **technically-assessable**
surface of the guide — every section below is exercised by a real HEAVEN detector
or tool feature, named explicitly, that produces evidence only from observed
behaviour (never fabricated). A handful of the guide's review techniques
(documentation review, log review, on-wire sniffing, file-integrity baselining,
social engineering, and assessment-policy development) have **no autonomous-scan
footprint**; they are listed per section as **out-of-band (analyst-attested)**
and are deliberately not scored — HEAVEN never asserts a result it cannot
evidence.

## Coverage summary

| Section | Coverage level |
|---|---|
| §3 Review Techniques | config & ruleset review automated; doc/log/sniffing analyst-attested |
| §4 Target Identification & Analysis | automated (recon + scanners) |
| §5 Target Vulnerability Validation | automated (auth cracking + orchestration) |
| §6 Security Assessment Planning | automated (engagement DB, scheduling, scope, authorization) |
| §7 Security Assessment Execution | automated (orchestrator, analysis, data handling) |
| §8 Post-Testing Activities | automated (remediation, reporting, retest) |

## Detailed mapping

### §3 Review Techniques
| NIST topic | HEAVEN module(s) |
|---|---|
| §3.3 Ruleset Review | `heaven.recon.firewall_detector` (firewall / IDS-IPS / tarpit / WAF classification from filtered-vs-closed tallies — the *effect* of the ruleset, measured externally) |
| §3.4 System Configuration Review | `heaven.vulnscan.ssl_scanner` (TLS config), `heaven.vulnscan.misconfig_scanner` (headers / cookies / server config), `heaven.recon.container_scanner` (k8s config) |

**Out-of-band (analyst-attested):** §3.1 Documentation Review, §3.2 Log Review,
§3.5 Network Sniffing (passive on-wire capture, impossible for a remote scanner)
and §3.6 File Integrity Checking (needs a host baseline/agent) have no
external-scan footprint — the assessor performs them directly. HEAVEN never fakes
them.

### §4 Target Identification & Analysis Techniques
| NIST topic | HEAVEN module(s) |
|---|---|
| §4.1 Network Discovery | `heaven.recon.network_scanner` (async port scan, OS fingerprinting heuristics) |
| §4.2 Network Port and Service Identification | `heaven.recon.network_scanner` (service fingerprint table + UDP probes) |
| §4.3 Vulnerability Scanning | the full `heaven.vulnscan` package (`heaven.vulnscan.cve_mapper`, `heaven.vulnscan.injection_scanner`, …) |

RF/monitor-mode 802.11 sniffing remains out of scope (requires local radio hardware a remote autonomous scanner cannot have) — never faked. |

### §5 Target Vulnerability Validation
| NIST topic | HEAVEN module(s) |
|---|---|
| §5.1 Password Cracking | `heaven.vulnscan.auth_scanner` (brute-force + default-cred check) |

**Out-of-band (analyst-attested):** §5.3 Social Engineering is out of scope for

## Audit-trail features (NIST 800-115 implicit requirements)

NIST emphasizes auditability throughout. HEAVEN supports this via:

- **Audit log**: every scan action logged (JSON-structured) under the engagement data dir
- **Evidence packaging**: `heaven.devsecops.evidence` produces replayable repros
- **Engagement DB**: SQLite per engagement, contains full scan history, scope changes, finding status updates
- **Operator notes**: each finding has an `operator_notes` field, modifiable via `heaven mark <id> <status> --notes "..."`
- **Chain-of-custody**: timestamps on every event (`first_seen_at`, `last_seen_at`)
